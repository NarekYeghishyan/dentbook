# ADR-0015. Своя (разовая) услуга врача в Mini App

Дата: 2026-10-03
Статус: принято

## Контекст

Врач записывает своего клиента в Mini App только на услуги, которые ему назначила
клиника. Владелец попросил «свою услугу»: врач сам вводит название и длительность,
выбирает время и записывает клиента. Такая услуга разовая — при следующей записи в списке
её быть не должно. По его ответу 2026-10-03 время выбирается из той же сетки: она
пересчитывается под введённую длительность, в рабочее время и мимо других записей и
закрытого времени.

`appointments.service_id` — обязательная ссылка на `services`, и название услуги во всех
местах (расписание, журнал, карточка клиента, CSV, алерты врачу, статус записи на сайте)
берётся через неё.

## Решение

- **Разовая услуга — строка `services` с `one_time = true`**, по одной на запись. Её
  создаёт `POST /v1/miniapp/appointments` с `customService: { name, durationMin }` вместо
  `serviceId`, в той же транзакции, что и запись. Буфера нет, цены нет, `is_public = false`.
  `appointments` не меняется, и название показывается везде как у обычной услуги.
- **В списки не попадает.** Каталог в панели (`GET/PATCH /v1/admin/services`) её не видит
  — 404. Назначить её врачу нельзя (`PUT /dentists/:id/services` — 404). В Mini App её нет,
  потому что список услуг врача строится по `dentist_services`. Виджет её не видит: CHECK
  `services_one_time_hidden` (`NOT one_time OR NOT is_public`) держит это на уровне БД
  (§2.5).
- **Второй записи на неё нет.** Mini App принимает только услуги врача из
  `dentist_services`, журнал — тоже. Холд с её id получает 404.
- **Сетка.** `GET /v1/miniapp/slots` принимает `durationMin` (5–480 мин) вместо
  `serviceId`. Движок доступности считает разовую услугу так же, как обычную, с
  длительностью из запроса и без буфера. Свободное время по-прежнему не хранится (§2.4).
  Кеш слотов для неё выключен: в ключе кеша нет её id.
- **Перенос.** Разовая услуга ни за кем не закреплена. Для неё движок берёт врача из
  запроса без `dentist_services`, поэтому запись переносит и врач, и регистратура. В
  журнале её можно перенести к другому работающему врачу.

Отвергнуто: `service_id` NULL плюс название в `appointments`. Пришлось бы менять каждое
соединение с `services` и каждый тип со `serviceId`, а `schema.sql` — сильнее.

## Последствия

- В `services` копятся строки разовых услуг, по одной на такую запись. Их не видно ни в
  одном списке, и места они почти не занимают.
- Отчёты и CSV показывают название разовой услуги как есть: одинаковые названия разных
  записей не сливаются в одну услугу.
- Регистратура записать на разовую услугу не может — только перенести или отменить уже
  созданную врачом запись. Своя услуга в журнале — отдельная задача.
