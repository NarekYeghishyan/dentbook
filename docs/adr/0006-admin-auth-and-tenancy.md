# ADR-0006. Сессии админки, роли и изоляция тенантов

Дата: 2026-09-18
Статус: принято

## Контекст

CLAUDE.md задаёт «сессию на JWT» для `/v1/admin` (§7), изоляцию тенантов (§2.2) и роли
(Шаг 3), но не говорит, где хранится токен, как защищаться от CSRF и перебора паролей, что
разрешено каждой роли и чем отвечать на занятый email. Админка живёт на том же домене,
что и API (Q14).

## Решение

- **Токен — в httpOnly-cookie** `dentbook_session` (`SameSite=Strict`, `Path=/v1/admin`,
  `Secure` в проде). JavaScript админки токен не видит, поэтому XSS не может его украсть.
  CSRF закрывают `SameSite=Strict` и JSON-тела: HTML-форма с чужого сайта JSON не пошлёт,
  на другой тип Fastify отвечает 415.
- **В токене только id пользователя.** Роль, активность и клиника читаются из БД на каждом
  запросе: отключение сотрудника и смена роли действуют сразу. Refresh-токенов нет —
  сессия живёт `JWT_ACCESS_TTL` (12 ч), потом вход заново.
- **Пароли — `scrypt` из `node:crypto`** (N = 2^15, r = 8, p = 1), параметры хранятся в
  строке хеша. Вход по несуществующему email тоже проверяет хеш — время ответа не выдаёт,
  есть ли такой email.
- **Лимит на вход и регистрацию** — `AUTH_RATE_LIMIT` попыток в минуту с IP. `trustProxy`
  доверяет одному звену (nginx), иначе IP подделывается через `X-Forwarded-For`.
- **Роли** (по комментариям `schema.sql`, согласованным в Q9):

  | Действие                                | owner | admin | registrar |
  | --------------------------------------- | :---: | :---: | :-------: |
  | `/me`, чтение настроек клиники          |   ✓   |   ✓   |     ✓     |
  | изменение настроек клиники              |   ✓   |   ✓   |           |
  | сотрудники: список, создание, изменение |   ✓   |   ✓   |           |

  `owner` появляется только при регистрации клиники; его роль и активность не меняются, а
  редактировать его может лишь он сам. Никто не меняет свою роль и не отключает себя.
  Сотрудников не удаляют, а отключают — их id остаются в `created_by`. `operator` в
  клинические роуты не пускается (панель оператора — Шаг 10).

- **Изоляция тенантов.** Все роуты, кроме `/auth/*`, — в области с хуком `authenticate`.
  `clinicId` берётся только из сессии и входит в каждый запрос к данным; id из пути без
  него ничего не открывает. Чужая или несуществующая сущность и id не в формате UUID —
  одинаково 404.
- **Тест изоляции** собирает роуты `/v1/admin` из самого приложения (`onRoute`) и требует
  на каждый проверку доступа к чужой клинике. Новый роут без такой проверки роняет тест.
- **Занятый email** — `409` с кодом `validation_failed`: отдельного кода в §7 нет, админка
  различает случай по статусу.
- **Ошибки БД в логах** — только SQLSTATE, таблица и ограничение: в сообщении
  `DrizzleQueryError` и в `detail` Postgres лежат параметры запроса (email, телефоны, §2.6).

## Последствия

- Счётчики лимита в памяти процесса. TODO(Шаг 5): хранилище в Redis — при нескольких
  процессах API лимит считается в каждом отдельно.
- Смена пароля не завершает уже выданные сессии: они живут до истечения. Если понадобится
  «выйти на всех устройствах» — колонка `users.sessions_valid_after` и сверка с `iat`.
- Приглашений по email нет: админ задаёт сотруднику начальный пароль сам.
- Один запрос в БД на каждый запрос админки ради актуальной роли — приемлемо для панели
  клиники.
