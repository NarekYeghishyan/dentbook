# ADR-0003. Опорная схема БД

Дата: 2026-09-17
Статус: принято, согласовано заказчиком 2026-09-17 (Q9)

## Контекст

CLAUDE.md §5 ссылается на `schema.sql`, которого не было. Заказчик поручил составить его
(Q1). Даны только имена 16 сущностей и инварианты §2.

## Решение

`schema.sql` в корне — справочник для переноса в Drizzle. Ключевые решения:

1. **Тенантность в самой БД.** Кроме `clinic_id` в каждой таблице данных, все ссылки
   между сущностями — составные FK `(clinic_id, x_id) → x (clinic_id, id)`. Запись
   клиники A с врачом, услугой, филиалом или клиентом клиники B отклоняется с `23503`.
   Это вторая линия защиты для §2.2; фильтр по `clinic_id` в запросах всё равно
   обязателен.
2. **Холд — строка `appointments` со `status = 'hold'`.** Иначе EXCLUDE-ограничение §2.1
   не видит удерживаемый слот. `hold_id` = `appointments.id`. Снятый холд → `expired`.
3. **Ограничение §2.1 перенесено дословно.** Буфер в него не входит (Q11).
4. **`working_hours` хранит настенное время** (`time`) в поясе филиала, остальное —
   `timestamptz`. «9:00» должно оставаться 9:00 после перехода на летнее время.
   Смена через полночь — одна строка с `end_time <= start_time`.
5. **Перечисления — `text` + `CHECK`**, а не `CREATE TYPE ... AS ENUM`: добавление
   значения — обычная миграция, без особенностей `ALTER TYPE`. Списки значений живут в
   `packages/shared/src/domain.ts`, из них строятся и CHECK в Drizzle-схеме.
6. **Удаление.** FK без каскада: клинику, врача, услугу, по которым есть записи,
   удалить нельзя — только деактивировать (`is_active`, `status`). Каскад только у
   `dentist_services`, `working_hours`, `schedule_exceptions`, `telegram_link_tokens`.
7. **Секреты в БД.** Код SMS — HMAC-SHA256 с серверным секретом; токен привязки
   Telegram — SHA-256. `api_keys.token` (публичный по природе) и
   `appointments.public_token` (нужен в тексте напоминаний) хранятся открыто.
8. **ПДн.** `notifications` не хранит текст сообщений, только вид шаблона.
9. **Исключение из тенантности** — `telegram_updates`: бот один на платформу.
10. **Операторы платформы** — строки `users` с `role = 'operator'` и
    `clinic_id IS NULL`; связь закреплена `CHECK`.
11. **Подтверждение записей** — настройка клиники `clinics.booking_requires_confirmation`
    (Q9): `false` — запись из виджета сразу `confirmed`, `true` — `pending` до
    подтверждения врачом или регистратурой. Записи от сотрудников и врачей подтверждены
    сразу. Судьба неподтверждённых записей — Q12.

## Перенос в Drizzle

Drizzle-DSL не описывает `CREATE EXTENSION`, `EXCLUDE USING gist` и gist-индекс по
выражению `tstzrange(...)`. Они идут кастомными миграциями (`drizzle-kit generate --custom`),
которые применяет тот же `drizzle-kit migrate` — требование §9 не нарушается.
`citext` описан через `customType`.

Порядок миграций:

1. `0000_extensions` — кастомная: `btree_gist`, `pgcrypto`, `citext`. Идёт первой, потому
   что таблицы используют `citext`.
2. `0001_init` — сгенерирована drizzle-kit из `packages/db/src/schema`.
3. `0002_appointments_no_overlap` — кастомная: EXCLUDE из §2.1 и gist-индекс
   `schedule_exceptions_dentist_range_idx`.

drizzle-kit сравнивает схему со снимками, а не с живой БД, поэтому объекты из кастомных
миграций не всплывают в следующем `generate` как «лишние». По той же причине
`drizzle-kit push` в проекте не используется: он сверяется с живой БД и предложил бы их
удалить.

Имена FK в Drizzle заданы явно и совпадают с автоматическими именами Postgres
(`<таблица>_<колонка>_fkey`), иначе каталоги двух БД расходятся.

## Проверка

- `schema.sql` прогнан на встроенном Postgres (PGlite 0.5.8, PostgreSQL 18.3): 61 проверка —
  EXCLUDE (пересечение, другой часовой пояс на входе, касание границ, холд, отменённые
  записи), составные FK между клиниками, все CHECK/UNIQUE, значения по умолчанию.
- Паритет Drizzle со `schema.sql` проверяет `packages/db/test/schema.integration.test.ts`:
  в контейнере PostgreSQL 16 рядом с мигрированной БД создаётся эталонная из `schema.sql`,
  и сравниваются расширения, колонки (тип, NULL, значение по умолчанию), ограничения и
  индексы. Там же — тест на 50 конкурентных записей на один слот.

## Последствия

- Любой запрос на вставку обязан передавать `clinic_id` — это и так требование §2.2.
- Составные FK требуют `UNIQUE (clinic_id, id)` у родительских таблиц — избыточный
  при uuid-ключе индекс ради гарантии изоляции.
- Схема меняется в двух местах сразу: Drizzle и `schema.sql`. Цена — дублирование,
  выгода — справочник, который невозможно забыть обновить: тест паритета упадёт.
- Решения, помеченные `TODO` в `schema.sql`, пересматриваются по мере ответов на Q10-Q12.
