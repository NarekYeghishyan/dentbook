# ADR-0013. Панель оператора, нагрузочный тест и сдача

Дата: 2026-09-18
Статус: принято

## Контекст

Шаг 10: панель оператора, нагрузочный тест, документация API, инструкция по встраиванию,
деплой. Критерий: 50 одновременных попыток записи на один слот дают ровно одну запись.
Q18: оператор видит клиники и приостанавливает их, следит за состоянием платформы. Боевого
сервера пока нет.

## Решение

- **Оператор** — строка `users` с `role = 'operator'` и без клиники (ADR-0003):
  - Регистрации через API нет. Учётную запись создаёт или сбрасывает команда на сервере
    `apps/api/src/create-operator.ts`: пароль генерируется и печатается один раз.
  - Вход — общий `POST /v1/admin/auth/login`. Теперь он отвечает `200 { role }`: панель по
    роли ведёт оператора в `/admin/operator`, сотрудника — в журнал.
  - Роуты — `/v1/admin/operator/*`: там же живёт cookie сессии. Свой хук
    `authenticateOperator` пускает только активного оператора. Клинические роуты оператора
    по-прежнему не пускают, а сотрудников клиник — к оператору (тест изоляции).
- **Что видит оператор.** Только сводные числа (врачи, визиты за 30 дней, последняя
  запись) и владельца клиники. Клиентов клиник, их телефонов и записей нет.
  - Ошибки доставки — по каналу и коду (`last_error`), без текста и получателей (§2.6).
  - Очереди — счётчики BullMQ `sms` и `telegram` (`getJobCounts`).
- **Приостановка** — `clinics.status = 'suspended'`. Всё, что уже проверяло статус,
  работает сразу:
  - форма записи — `invalid_key`;
  - панель клиники — 403;
  - Mini App — 403.

  Добавлено: бот не подключает врачей и не подтверждает записи приостановленной клиники.
  Назначенные визиты не отменяются, клиентам по-прежнему уходят напоминания: пациенты не
  должны страдать из-за счетов клиники.

- **Нагрузочный тест:**
  - Инструмент `apps/api/src/load-test.ts` работает против любого развёртывания: N
    одновременных холдов одного слота, сводка статусов и задержек, холды победителей
    отпускаются.
  - Критерий шага проверяет `apps/api/test/load.integration.test.ts`: тот же код против
    настоящего HTTP-сервера на Testcontainers. 50 одновременных холдов → 1 холд и 49
    `slot_taken`. Затем 50 одновременных подтверждений выигравшего холда → ровно одна
    запись в БД.
  - Против стенда прогон ограничен лимитом холдов с IP (10 в минуту). Это проверено, и
    лимит сработал как задумано.
- **Документация** — на английском, для клиник и их разработчиков:
  - [docs/api/public-api.md](../api/public-api.md) — публичный API §7: вход, лимиты,
    ошибки, поток записи, все роуты с примерами;
  - [docs/embed.md](../embed.md) — встраивание формы: ключ, код, WordPress / Squarespace /
    Wix, CSP, неполадки.

  Внутренний админский API отдельно не документируется: его единственный клиент — наша
  панель, а контракт — типы `@dentbook/shared`.

- **Эксплуатация:**
  - `deploy/backup.sh` — `pg_dump` с ротацией 14 дней по cron;
  - ротация логов контейнеров (`json-file`, 5 × 10 МБ);
  - чек-лист боевого запуска в `deploy/README.md`: 10DLC для SMS в США, домены Turnstile,
    внешняя проверка `/health`, копии вне сервера.

## Последствия

- Боевой деплой не выполнен: ждёт VPS клиента (Q18). Всё для него описано и проверено на
  стенде тем же `deploy.sh`.
- Резервные копии лежат на том же сервере. Копирование наружу — часть чек-листа, скриптом
  не делается: способ зависит от провайдера сервера.
- У оператора нет смены пароля в панели: сброс — повторным запуском команды на сервере.
