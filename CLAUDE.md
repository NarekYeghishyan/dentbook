# CLAUDE.md — Dental Booking Platform

Файл читается в начале каждой сессии. Правила ниже действуют постоянно.

---

## 1. Что строим

Мультитенантная SaaS-платформа онлайн-записи для стоматологических клиник.

Клиника регистрируется, заводит врачей, услуги и расписание, получает API-ключ и встраивает форму записи на свой сайт. Клиент выбирает услугу и свободное время — врач назначается автоматически по приоритету. Врачи работают через Telegram: получают алерты, управляют своим временем, записывают собственных клиентов.

**Клиент платформы — клиника. Конечный пользователь формы — клиент клиники (пациент).**

## 2. Жёсткие инварианты

Нарушение любого из этих пунктов — критический баг, а не замечание по стилю.

### 2.1. Двойная бронь невозможна на уровне БД

Проверка «SELECT пересечения, затем INSERT» неприемлема — между запросами гонка. Только ограничение БД:

```sql
CONSTRAINT appointments_no_dentist_overlap EXCLUDE USING gist (
  dentist_id WITH =,
  tstzrange(start_at, blocked_until) WITH &&
) WHERE (status IN ('hold', 'pending', 'confirmed'))
```

`blocked_until = end_at + buffer_min` — запись держит время вместе с буфером после приёма, поэтому буфер тоже защищён от гонки (решение Q11). Колонку заполняет код, соответствие проверяет CHECK.

Требует `CREATE EXTENSION btree_gist`. Код должен корректно обрабатывать ошибку `23P01` (exclusion_violation) и возвращать клиенту `slot_taken` с альтернативными слотами.

### 2.2. Изоляция тенантов

`clinic_id` проверяется в каждом запросе к данным. Ни один запрос не должен полагаться только на переданный id сущности. На каждый публичный и админский эндпоинт — тест на попытку доступа к данным чужой клиники.

### 2.3. Время

Хранение — `timestamptz` в UTC. Все вычисления в UTC. Форматирование в часовом поясе филиала (или клиники, если у филиала не задан). Никогда не использовать локальный пояс сервера.

### 2.4. Свободные слоты не хранятся

Доступность вычисляется на каждый запрос из рабочих часов, записей и исключений расписания. Таблицы «свободных слотов» быть не должно — она неизбежно рассинхронизируется.

### 2.5. Публикуемый ключ не даёт лишнего

`pk_*` живёт в браузере. Его права: чтение доступности и создание записи. Ничего больше. Проверка заголовка `Origin` против `allowed_origins` ключа, иначе 403.

### 2.6. Персональные данные не попадают в логи

Телефоны, email, ФИО клиентов не логируются и не уходят в трекеры ошибок. В логах — только идентификаторы.

`packages/core` не импортирует ничего из `apps/` и не обращается к БД напрямую — только чистые функции над переданными данными. Так движок доступности покрывается быстрыми unit-тестами.

## 5. Модель данных

Опорная схема — в `schema.sql` в корне репозитория. Перенести её в Drizzle без изменения имён таблиц и полей.

Ключевые сущности: `clinics`, `locations`, `users`, `api_keys`, `dentists`, `services`, `dentist_services`, `resources`, `working_hours`, `schedule_exceptions`, `patients`, `appointments`, `notifications`, `telegram_link_tokens`, `telegram_updates`, `phone_verifications`.

Названия в БД оставить как в `schema.sql` (`patients`, `clinics`). В интерфейсе и текстах для пользователя использовать «client» и «office» — так в договоре с заказчиком.

## 6. Движок доступности

`packages/core/src/availability.ts`, чистая функция:

```ts
function computeSlots(input: {
  workingHours: Interval[];      // на запрошенную дату, UTC
  exceptions: { type: 'block' | 'extra'; interval: Interval }[];
  appointments: { interval: Interval; bufferMin: number }[];
  durationMin: number;
  bufferMin: number;
  stepMin: number;
  notBefore: Date;               // now + min_lead_min
}): Date[]
```

Порядок:

1. база = `workingHours`
2. плюс интервалы `exceptions.type === 'extra'`
3. минус интервалы `exceptions.type === 'block'`
4. минус интервалы `appointments`, расширенные на свой `bufferMin`
5. минус всё раньше `notBefore`
6. нарезка сеткой `stepMin`; слот валиден, если влезает `durationMin + bufferMin`

Для запроса «любой врач» — объединение слотов всех врачей, оказывающих услугу, с дедупликацией по времени начала.

**Назначение врача при записи:** среди свободных на выбранное время — минимальный `priority`; при равенстве — меньше записей в этот день; при равенстве — случайно.

Кеш: Redis, ключ `avail:{clinic}:{dentist}:{date}:{service}`, TTL 60 с, инвалидация при любом изменении записей или расписания этого врача.

## 7. Публичный API

Префикс `/v1/public`, аутентификация `Authorization: Bearer pk_...`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/config` | настройки виджета: язык, пояс, цвета, филиалы |
| GET | `/services` | публичные услуги |
| GET | `/availability` | свободные слоты: `service_id`, `location_id`, `from`, `to` |
| POST | `/holds` | удержать слот, вернуть `hold_id` и `expires_at` |
| DELETE | `/holds/:id` | отменить удержание |
| POST | `/verifications` | отправить SMS-код |
| POST | `/appointments` | подтвердить запись: `hold_id`, данные клиента, код |
| GET | `/appointments/:id` | статус по публичному токену |
| POST | `/appointments/:id/cancel` | отмена клиентом по токену |

Админский API — `/v1/admin`, сессия на JWT, полный CRUD.

Формат ошибок единый, коды стабильные и перечислены в `packages/shared/src/errors.ts`:

```json
{ "error": { "code": "slot_taken", "message": "..." } }
```

Коды: `invalid_key`, `origin_not_allowed`, `rate_limited`, `slot_taken`, `hold_expired`, `verification_required`, `verification_failed`, `outside_working_hours`, `validation_failed`, `unauthorized`, `forbidden`, `not_found`, `internal_error`.

## 8. Telegram

**Привязка врача.** Админка генерирует одноразовый токен → `t.me/<bot>?start=<token>`, TTL 24 ч. Бот сверяет токен, пишет `telegram_chat_id` в `dentists`.

**Обязательно:**

- webhook, не polling;
- дедупликация по `update_id` через таблицу `telegram_updates` — Telegram ретраит доставку;
- ошибка 403 (бот заблокирован) → выставить `telegram_blocked`, не ретраить бесконечно;
- отправка сообщений только через очередь BullMQ с backoff.

**Mini App.** Авторизация по `initData`: HMAC-SHA256, секрет — `HMAC('WebAppData', BOT_TOKEN)`. Проверять подпись **и** свежесть `auth_date` (не старше 1 часа). Врач находится по `user.id` = `dentists.telegram_chat_id`. Реализация — `apps/api/src/telegram/verify-init-data.ts`, покрыть тестом на подделанную подпись.

**Правило:** врач не может закрыть время, на котором есть запись. Возвращать список этих записей и требовать переноса через регистратуру. Автоотмена записей запрещена.

## 9. Конвенции

- Миграции только через drizzle-kit, руками SQL в БД не применять.
- Все входные данные валидируются zod-схемами из `packages/shared`.
- Конфигурация — переменные окружения, разбор через zod при старте, падать при отсутствии обязательных. Шаблон в `.env.example`.
- Логи структурированные (pino), сквозной `request_id`.
- Тексты интерфейса — в файлах переводов, строк в коде нет. Базовый язык — английский.
- Денежные суммы — `numeric`, не float.
- Коммиты по Conventional Commits.

## 10. Порядок работы

Выполнять последовательно. Не начинать следующий шаг, пока в текущем не выполнено «Готово».

**Шаг 1 — каркас и БД.** Монорепо, docker-compose с Postgres и Redis, схема в Drizzle, миграции, сиды.
*Готово:* `pnpm migrate` и `pnpm seed` проходят на чистой БД; ограничение `EXCLUDE` подтверждено тестом на конкурентную вставку.

**Шаг 2 — движок доступности.** `packages/core`, чистые функции, unit-тесты.
*Готово:* покрытие не ниже 90%; тесты на буферы, исключения обоих типов, границы рабочих часов, переход через полночь, переход на летнее время.

**Шаг 3 — аутентификация и тенантность.** Регистрация клиники, вход, роли, middleware проверки `clinic_id`.
*Готово:* тест на доступ к данным чужой клиники падает с 404/403 на каждом эндпоинте.

**Шаг 4 — админский API и панель.** Врачи, услуги, рабочие часы, исключения, филиалы, приоритет перетаскиванием.
*Готово:* клиника может с нуля завести данные и увидеть корректный календарь доступности.

**Шаг 5 — ключи и публичный API.** Выдача и отзыв ключей, проверка Origin, rate limit, холды.
*Готово:* холд истекает и слот возвращается; конкурентное подтверждение одного слота даёт ровно одну запись.

**Шаг 6 — виджет.** Форма, верификация телефона, капча, адаптивность.
*Готово:* запись создаётся end-to-end на тестовой странице; бандл меньше 50 КБ gzip.

**Шаг 7 — бот и Mini App.** Привязка, алерты с кнопками, расписание, блокировка времени, запись своих клиентов.
*Готово:* врач проходит весь цикл в Telegram без админки.

**Шаг 8 — уведомления.** SMS-провайдер, шаблоны, напоминания за 24 ч и 2 ч, отмена напоминаний при отмене записи.
*Готово:* напоминания ставятся и снимаются, повторные попытки работают.

**Шаг 9 — журнал и отчёты.** Календарь день/неделя, drag-and-drop с проверкой конфликтов, карточка клиента, выгрузка CSV, дашборд.
*Готово:* перенос записи мышью не создаёт пересечений.

**Шаг 10 — сдача.** Панель оператора, нагрузочный тест, документация API, инструкция по встраиванию, деплой.
*Готово:* 50 одновременных попыток записи на один слот дают ровно одну запись.

## 12. Правила для агента

- **Не расширять объём.** Всё, чего нет в этом файле, — отдельная задача. Заметил пробел в требованиях — спроси, не додумывай.
- **Не оставлять моков в рабочем коде.** Фикстуры живут в тестах.
- **Не хранить секреты в репозитории.** Только `.env`, в `.env.example` — пустые значения.
- **Не писать «примерно работающие» вычисления времени.** Любая логика с датами покрывается тестом, включая переход на летнее время и работу через полночь.
- **Не заменять ограничение БД проверкой в коде.** См. пункт 2.1.
- **Перед правкой существующего файла прочитать его целиком**, а не патчить по фрагменту.
- **После каждого шага** прогонять `pnpm lint && pnpm test` и не переходить дальше при падении.
- Сомневаешься между простым и «правильным на будущее» решением — выбирай простое и оставь `TODO` с причиной.
